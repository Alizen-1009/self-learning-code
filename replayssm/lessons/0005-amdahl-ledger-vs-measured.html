ReplaySSM · 第 5 课

账本 vs 实测

前四课算出来的账都很漂亮：kernel 级 1.4–1.8×。但 SGLang 把它接进 Qwen3.5（MoE）后，端到端只快了 2.3%。这不是谁算错了 —— 是两张成绩单量的不是同一个东西。这一课把换算关系补上，然后回答真正的问题：什么配置才值得写这个 kernel。

收获 落差 换算 反推 配对读数 算盘 另两个轴 检查 检索
本课唯一收获

能从实测的端到端加速反推被加速部分的时间占比，用它解释「kernel 1.2–1.5× vs 端到端 2.3%」的落差，并给出「要不要写 kernel」的判断依据。

三个新符号，也是全部符号：f（GDN decode 占端到端时间的比例）、x（对这一段的局部加速）、E（端到端加速）。前四课的 d n h L T 这一课全部退场 —— 它们的工作已经完成，都被打包进了 x。

两张成绩单

同一套算法，两份实测：

来源模型kernel 加速端到端
博客 §6Nemotron-3 / Qwen3.5，至 550B1.43–1.84×1.20–1.48×

注意 kernel 那一列：两边基本一致。1.2–1.5× 与 1.43–1.84× 是同一个量级 —— kernel 层没有任何矛盾，前四课的账没有算错。

分歧全在最后一列。同样的 kernel 加速，一边换来 1.20–1.48×，一边只换来 1.023×。差别不在 kernel，在 kernel 之外的时间。

decode 一个 token 的时间里，GDN 层的 state 读写只是其中一段。对 MoE 模型，大头在别处：expert FFN 的权重搬运、full-attention 层的 KV cache、路由与通信。ReplaySSM 只加速 GDN 那一段 —— 其余部分一纳秒都不会变快。

换算关系：一行推导

把 decode 一个 token 的时间归一化为 1，其中 GDN 段占 f，其余占 1 − f。给 GDN 段加速 x 倍，新的总时间是 (1 − f) + f/x。端到端加速就是两个时间之比：

E = 1 / ( (1 − f) + f/x ) Amdahl 定律。整门课最短的推导 —— 但它决定前四课的成果能兑现多少。

两个立即成立的推论（都已数值验证）：

E ≤ x   （端到端永远不超过局部加速）
E ≤ 1 / (1 − f)   （x → ∞ 时的上限：没被加速的部分成为地板） 第二条是本课最有杀伤力的一句话：f 一旦定了，kernel 写得再完美也突破不了 1/(1−f)。

把公式倒过来，就得到本课真正的工具 —— 从两个实测值反推 f：

f = ( 1 − 1/E ) / ( 1 − 1/x ) E 与 x 都能测：E 来自端到端 benchmark，x 来自 kernel microbench。f 不用 profile 就能估出来。

反推：MoE 里的 GDN 只占 9%

把 SGLang 的两个实测代进去：E = 1.023（+2.3% TPOT），x 取 microbench 中值 1.35：

f = ( 1 − 1/1.023 ) / ( 1 − 1/1.35 ) ≈ 8.7% 取 x 的两端 1.2 / 1.5，则 f 落在 13.5% / 6.7% 之间。结论不变：GDN decode 在这个 MoE 模型里只占一成上下。

2.3% 于是完全说得通 —— 甚至可以说 kernel 已经把能拿的基本拿完了。看 f = 8.7% 时把 x 继续往上推能买到什么：

kernel 从 1.35× 推到无限快，端到端只从 1.023× 涨到 1.095×。

这就是「要不要继续优化 kernel」的答案：对这个 MoE 配置，不要。剩下的 91.3% 时间在 expert FFN 和 attention 里，优化预算应该去那边。

这个 f 是一阶模型下的有效占比：假设加速只作用于 GDN 段、其余时间不变，调度与 kernel launch 开销都归进 1 − f。真实系统里各段有重叠与相互影响，所以它是估计而非 profile 读数 —— 但做「值不值得」这个量级判断足够了。RFC 自己的判断（dense GDN 模型收益应更大）用的正是同一个逻辑。

看到别人的 benchmark 时

先做 E ≤ x 检查，再反推 f 看是否落在 (0, 1) 且符合模型结构的常识。任何「端到端加速超过 kernel 加速」的声明，要么测量有误，要么加速的不止那一段（比如顺带减少了同步或显存压力 —— 那就该在正文里说清楚）。

反过来看，博客配置反推出 f ≈ 55–71%：它测的是 SSM 层占大头的 dense 模型。这与 RFC 的判断互相印证 —— 同一套 kernel，落差完全由 f 解释，两张成绩单从头到尾没有矛盾。

试三个位置：① 预设（MoE 实测）；② f 拉到 55–71%（博客的 dense 配置）—— 同一个 x，端到端立刻到 1.2–1.5×；③ f 不动、x 拉满 —— 看 E 怎么贴着上限不动。

Amdahl 只压一个轴

到这里容易得出一个过头的结论：「MoE 上 ReplaySSM 不值得」。但 2.3% 只是时间轴上的读数，而这套东西的收益有三个轴，Amdahl 只管第一个：

  • 时间（TPOT）—— 受 f 压制

    本课主题。E ≤ 1/(1−f)，MoE 上限 1.095×，dense 上限 2.2–3.5×。这是唯一被 Amdahl 管辖的轴。

  • 显存 / 并发 —— 不受 f 压制

    不存 state 快照、buffer 远小于 state，省的是 HBM 容量。博客实测：固定 HBM 预算下并发 3.0–3.3×。显存省下来就是省下来了，与 GDN 段占多少时间无关 —— Amdahl 公式里根本没有这一项。

  • 能力解锁 —— Amdahl 不适用

    没有 ReplaySSM 之前，SSM 上的投机解码要么每 draft 存一份 state 快照（Snakes and Ladders，4dn/draft），要么串行验证。ReplaySSM 让投机变得可做（吞吐 1.87–1.96×）。「让做不了的事变得可做」不是「把已有环节加速 x 倍」—— 这类收益不在 Amdahl 的管辖范围内，用 f 去折算它是范畴错误。

所以「值不值得」的完整判断是

① 先测或反推 f。dense GDN、长上下文、大 state（d·n·heads 大）⟹ f 大，时间轴收益厚；MoE ⟹ f 小，时间轴收益薄。② f 小不等于不做 —— 显存/并发轴与投机解锁轴照常兑现，SGLang 照样合并了这个 RFC。③ 但优化 kernel 的边际投入要看 f：f = 8.7% 时把 kernel 从 1.35× 磨到 2× 只多买 2.2%，这个时间不如花在 expert FFN 上。

回到本工作区的正事。MISSION 里悬着的问题是「要不要开 B300 kernel 分支」。现在有了判断工具：先在目标模型上 profile 出 GDN decode 段的 f，套 E = 1/((1−f) + f/x)，用第 1–4 课的账估 x（带宽账给出的上限约 1.7×）。f·(1 − 1/x) 就是能赚到的全部时间 —— 数字摆出来，做不做一目了然。

检索练习（合上讲义）

第一题 · 推导。从「总时间归一化为 1」出发，写出 E(f, x) 与反推公式 f(E, x)，并说出两个推论（E ≤ x、上限）各自为什么成立。

第二题 · 反推。某模型实测端到端 E = 1.10，kernel microbench x = 1.6。求 f 和上限。这个配置继续磨 kernel 值不值？

第三题 · 决策。你的 B300 上有个 dense GDN 模型，profile 出 f = 40%，第 1–4 课的账估出 x ≈ 1.7。求端到端 E 与上限，并给出「做不做 kernel 分支」的判断和理由（提示：别忘了另两个轴）。

1. 加速后总时间 (1−f) + f/x，故 E = 1/((1−f) + f/x)；解出 f = (1−1/E)/(1−1/x)。E ≤ x：就算 f = 1（全部时间都被加速）也只能得到 x，少一点就更小。上限 1/(1−f)：x → ∞ 时 f/x → 0，剩下没被加速的 1−f 成为地板。

2. f = (1−1/1.10)/(1−1/1.6) = 0.0909/0.375 ≈ 24%，上限 1/0.758 ≈ 1.32×。已经拿到 1.10×，离 1.32× 的地板不远 —— kernel 从 1.6× 磨到 2× 只能再买几个百分点，边际收益薄，除非另两个轴（显存/投机）有需求，否则优化预算应转向那 76%。

3. E = 1/(0.6 + 0.4/1.7) = 1/0.835 ≈ 1.20×，上限 1/0.6 ≈ 1.67×。值得做：时间轴一项就有 20% 的端到端收益（与博客 dense 实测的下沿 1.20× 吻合）；且这还没算并发轴（固定 HBM 并发 3.0–3.3×）和投机解锁轴（1.87–1.96×）。判断依据写成一句话：f·(1−1/x) = 0.4 × 0.41 ≈ 16.5% 的总时间是这个 kernel 能赚到的钱。
