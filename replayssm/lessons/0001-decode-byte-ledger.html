一个矩阵，
从来不需要存在

decode 的每一步，都在把一个 128×128 的状态矩阵搬进搬出 HBM，只为换回 128 个数字。ReplaySSM 的全部想法压在一行结合律上。这一课只做一件事：把这笔账算清。

合上讲义能做到两件事：（一）说出 decode 单步的收支 —— 搬了多少字节、换回多少字节；（二）写出那一行结合律，并解释它为什么让 state 的写回整个消失。

这一课刻意不碰的东西：衰减权重的具体形式（第 3 课）、缓存窗口该取多长的正式推导（第 4 课）、GDN 为什么不能照搬这套（第 2 课）。它们各有专课。这里只建立一个支点。

符号：只有这些

上一版讲义在这一课里塞进了近二十个带上下标的符号，这是它最大的毛病。新规矩：凡是能写成数字的，一律写成数字；下标只出现在公式框里，正文里不出现。

  • d value 维 = 128
  • n key 维 = 128
  • S 状态矩阵 d×n
  • S₀ 检查点状态
  • k key，长 n
  • q query，长 n
  • v value，长 d
  • a 每步衰减，标量
  • w 标量权重
  • h 已缓存 token 数

全程 fp32、单个 head、d = n = 128。需要完整符号表（含 GDN 与投机解码那一套）时去公式卡，那是它该待的地方。

先算收支：decode 单步搬了什么

你在 linear_attn 第 2 课 推过这条递推。prefill 时你把序列切 chunk，用 GEMM 把它压成 compute-bound 的矩阵乘。decode 时序列长度是 1，chunk 没了 —— 麻烦全部来自这里。

S ← a · S + (v k⊤)      y = S q Mamba-2 的状态更新与读出。输入增益已折进 v，少一个符号，不影响任何结论。Tri Dao, ReplaySSM §1

这一行里藏着一笔极其难看的账。把它摊开：

Summary route · 每 head 每 step

满刻度 = 128 KiB。fp32，d = n = 128。

读旧状态 S 64 KiB
写新状态 S 64 KiB
换回的输出 y 512 B
搬运总量 ÷ 有用产出 128 KiB ÷ 512 B = 256 : 1

搬 128 KiB，换回 512 字节。整步的浮点运算量大约是 4dn ≈ 6.6 万 次，除以 13 万字节 —— 算术强度约 0.5 FLOP/byte，也就是博客说的 1 FLOP/byte 量级。现代 GPU 的算力与带宽之比是几百比一，所以这个 kernel 的时间几乎全部花在搬状态，而不是算它。博客 §2 指出：在混合模型里成为主要瓶颈的反而是 SSM 层，不是 attention 层。

顺带记住另外两笔账，第 3、4 课会回来收：状态更新是有损摘要，原始输入被扔掉了，所以投机解码被拒时无法回退；验证 T 个 draft 需要每个位置的中间状态，只能一个一个算，拿不到 Transformer 那种一次 GEMM 验证全部 draft 的并行度。

支点：一行结合律

整个方法压在这一行上。这一课如果只记一件事，记它。

(v k⊤) q  =  v (k⊤ q) 左边先造矩阵再读出；右边先把两个向量缩成一个标量，再拿它缩放一个向量。博客 §3

两边完全相等 —— 这是矩阵乘法的结合律，不是近似。但代价差得离谱：

左边：先造矩阵

v k⊤ 是一个 128×128 的外积，要算 16,384 个数并把它们放进内存；然后再拿 q 做一次 mat-vec 把它读出来。

而且必须物化一个 128×128

右边：先做内积

k⊤ q 是长度 128 的内积，得 一个标量；再用这个标量缩放长度 128 的 v。128 + 128 次乘法。

256次乘法
那个 128×128 从未出现

64 倍的差距只是表面收益。真正的收益是那句话：那个 128×128 的矩阵从来不需要存在。

换个角度想就通了：我们真正想要的东西是 y，一个长度 128 的向量。状态矩阵只是通往它的中间产物。而中间产物 —— 只要能绕过去 —— 是可以不存在的。

于是「内存里留什么」变了

递推有两种等价读法。区别不在数学，只在你把什么留在内存里。

Summary route · 留摘要

每步立刻把新输入吸收进状态，然后扔掉输入。状态是唯一的真相来源，所以每步都得把整个 128×128 读进来、写回去。

这就是标准 SSM decode 的做法，也是上面那笔 256:1 的账。

History route · 留输入

只保留一个检查点状态加上最近 h 个 token 的原始输入。需要状态时现场重建 —— 而配上结合律，连"重建"这一步都省了，直接算出 y。

这是 ReplaySSM。名字里的 replay 就是这个意思：把最近的输入重放一遍。

这是恒等变换，不是近似

最容易误读的一点：缓存窗口不是截断。窗口之前的全部历史，精确地、无损地活在检查点状态 S₀ 里。这和 sliding-window attention 完全是两回事 —— 后者真的把远处的 token 丢了，前者一个 token 都没丢。两条路线的输出在实数域上逐位相等。

把结合律代进 history route，状态就被彻底消掉了，只剩下向量运算：

y = w0 (S0 q)  +  Σj=1..h wj · vj · (kj⊤ q) output-only formulation。w 全都是由那串 a 的乘积算出来的纯标量 —— 具体形式第 3 课再展开，这里不需要。博客 §3

请只看一件事：右边没有任何 d×n 的矩阵参与运算。S₀ q 是一次 mat-vec，读了 S₀ 但没写它；求和号里全是标量乘向量。

# summary route：每步物化并写回整个 state
S = a * S + torch.outer(v, k)     # 128×128 读 + 128×128 写
y = S @ q                         # 再读一次刚写完的 state

# history route + 结合律：state 只读检查点，输入进 ring buffer
buf_k[pos], buf_v[pos] = k, v     # 追加原始输入，不做摘要
kq = buf_k @ q                    # (h,) 每个 token 一次长度-n 内积
y  = w0 * (S0 @ q) + (w * kq) @ buf_v   # 外积从未出现

伪代码用于对齐公式与数据流，不是官方实现。参考实现见 Johnny-Liou/ReplaySSM。

诚实标注：博客给出的头条数字是 state traffic 从 8dn 降到 4dn，也就是 128 KiB → 64 KiB 的 2×。上面这张图多算了一项「读 buffer」—— 那是本课程补的账，博客没把它计入。还有一项没画：buffer 满时要 flush 一次，把写回摊薄成每步 4dn/L 字节。所以 2× 是上界，实际收益取决于 h。下面的算盘就是让你亲手把这个取舍摸出来。

一次改动，三个答案

「不存摘要，存输入」这一个改动，同时回答了 decode 的三个痛点。这一段没有任何公式 —— 但它是整篇博客的立论。

  • 带宽不再写状态，state traffic 减半。原本花在写回上的那一半带宽直接省掉。
  • 回滚原始输入还在手上。投机解码拒了一个 draft，只需把 ring buffer 的写指针退回去 —— 零快照。既有做法是给每个 draft 存一份完整状态。
  • 并行y 只依赖检查点和 buffer，各 draft 位置之间没有串行依赖。逐个推进的循环变成一次 masked GEMM。
那状态什么时候还是要写？

buffer 快满时做一次 flush：把窗口里的输入汇总进检查点，清空 buffer，写回 HBM。这是唯一发生状态写回的时刻。判据、ring buffer 指针管理、以及它为什么是正确性不变量而不是性能旋钮 —— 是第 4 课的全部内容。这一课不碰。

检索练习

先在纸上算，算完再用算盘对答案。不要先拖滑块 —— 预测错了才记得住。

换一组不对称的配置：d = 128、n = 256、h = 64，fp32，单 head。求三个数：

  1. Summary route 每步搬多少字节？
  2. ReplaySSM 每步搬多少字节（含读 buffer）？
  3. 这组配置下缓存窗口的临界长度是多少？h = 64 在临界点的哪一侧？

1. 状态是 128×256 = 32,768 个 fp32 = 128 KiB。读加写 = 256 KiB。

2. 读检查点 128 KiB；buffer 每个 token 存一个长 128 的 v 和一个长 256 的 k，共 384 个数 = 1.5 KiB，64 个 token = 96 KiB。合计 224 KiB，只有 1.14× —— 比对称配置差得多。

3. 临界点是「一个 d×n 矩阵值多少个长度 d+n 的向量对」：128×256 ÷ (128+256) = 32,768 ÷ 384 = 85。h = 64 在临界点之内，还在赚，但余量已经不多。

留一个悬念给第 4 课：这里算出的 85 只是带宽给出的上界。真实的窗口长度还要同时满足投机窗口的余量要求，以及和 radix cache 的快照边界对齐。所以实际取值会明显小于 85 —— SGLang 干脆把它做成了可调参数 --gdn-replayssm-cache-len（RFC #28511）。

下一课：GDN 为什么不能照搬

这一课的结合律有一个前提：状态更新必须是「标量衰减 + 一个外积」。Mamba-2 正好是这个形状，所以直接缓存 k 和 v 就够了。

GDN 不是。delta rule 在状态的右边乘了一个投影矩阵，展不成「检查点 + 加权和」。ReplaySSM 的修补一句话就能说完：缓存一个伪 value 而不是 v，让更新退化回上面那个形状。而那个伪 value 你其实已经见过 —— 它就是你在 WY 表示里推过的修正项。

第 2 课把这条线接上，并算清 GDN 究竟多付了什么代价。答案可能和你猜的不一样：不是带宽（GDN 同样从不写回 state），而是窗口内的伪 value 串成了一条依赖链 —— 这条链正是第 3 课要用一次三角求解砍断的东西。
