三个不变量

前三课的风险是「推错公式」—— 一跑就露馅。这一课的风险完全不同：簿记错了程序不崩、不报错、不出 NaN，只是安静地算错。而且错得越轻，越危险。

收获 静默算错 状态机 三个不变量 回滚为何精确 L 的两侧 检查 检索
本课唯一收获

能凭记忆画出 cache / flush 状态机，说出三个正确性不变量各自「破了会怎样」，并从两侧夹出 L 的取值区间。

新增符号只有 m（一轮投机中被接受的 draft 数，0 ≤ m ≤ T）。其余全是老面孔：d n S₀ u k h L T w。这一课几乎没有新数学 —— 难点从「推导」换成了「不漏掉一个条件」。

先看后果：违反判据会发生什么

我写了一个 60 步的 GDN 序列，用两种方式跑：一种老实遵守 flush 判据，一种故意漏掉判据（让环形 buffer 自然回绕、覆盖旧数据）。两者都和纯递推基线对比：

相对误差 · 遵守判据 vs 漏掉判据（fp64，d=6, n=5, 60 步）
L遵守判据漏掉判据有没有报错？
41.6e-15281.8%没有
81.6e-15101.0%没有
161.6e-1536.9%没有
321.6e-150.6%没有

L 越大，错得越轻 —— 所以越危险。

L=4 时 282% 的误差你一眼就看见了。L=32 时只有 0.6% —— 输出量级正常、没有 NaN、短序列上看着像「精度问题」，能一路活到 benchmark，最后表现为长上下文质量莫名下降。

这就是为什么下面三条要叫不变量而不是「参数」：它们不是性能旋钮，是正确性条件。判错的代价不是慢，是错。

状态机

一轮投机解码的完整簿记流程。合上讲义后你应该能重画这张图 —— 这是本课的主要考点。

稳态 buffer 里有 h 个已提交 token 的 (u, k, a)；检查点 S₀ 在 HBM 里只读。此时的状态 = S₀ 加上 buffer 里那 h 项的加权和（第 1 课的展开）。

↓ 新一轮开始前，先问一个问题

h + 2T > L ？ 这一步是整套簿记唯一的正确性闸门。注意它问的是「装不装得下」，而不是「快不快」。
是 → 先 flush 装不下了，必须先腾空间。
否 → 直接进第 4 步 余量够，本轮不写 state。
FLUSH（唯一会写 state 的时刻） 把 buffer 里 h 项按 w 权重汇总进 S₀ → 写回 HBM → h = 0、write_pos = 0。成本 4dn 字节，摊薄到整个周期上。
APPEND：写入 T 个 draft 把 T 个 draft 的 (u, k, a) 写进 buffer。write_pos 在这里前进，且整个 forward 只前进这一次。
VERIFY：一次算完，不串行 三角求解出 T 个 u，masked GEMM 出 T 个 y（第 3 课）。全程不物化 state。
COMMIT / ROLLBACK：接受 m 个 把 write_pos 退到 h + m，然后 h ← h + m。被拒的 T − m 项就留在那里等着被覆盖 —— 不需要任何撤销动作。

↺ 回到稳态。整个循环里 S₀ 只被读，除了 FLUSH 那一步。

为什么是 2T 而不是 T？

装下本轮的 T 个 draft，只需要 h + T ≤ L。多留一轮余量的理由是下一条不变量：write_pos 每个 forward 只能前进一次，所以你不能在一轮中间临时插入一次 flush。判据必须提前一轮保证安全 —— 最坏情况是本轮全部接受（m = T），于是 h 变成 h + T，下一轮还得装得下另外 T 个。

⚠️ h + 2T > L 这个判据本身取自博客（并见公式卡）；上面这段「为什么是 2T」是我的重建，博客没有展开。它自洽且能解释为什么 2T 与 CUDA graph 约束绑在一起，但请当作推断而非原文。

三个不变量

  • h + 2T ≤ L

    环形 buffer 永远不能覆盖仍然需要的输入。窗口之前的历史都在 S₀ 里，窗口之内的必须字字完好 —— 因为它们是重建状态的唯一来源。

    破了会怎样：回绕覆盖掉还要用的 (u, k) → 重建出的状态少了几项 → 静默算错。上面那张表就是它，误差从 282% 到 0.6% 都有。

  • write_pos 每 forward 只前进一次

    这条不是数学要求，是 CUDA graph 要求。CUDA graph 把一次 forward 的 kernel 序列录下来重放，指针的推进次数必须是录制时固定的 —— 不能依赖运行时才知道的 m。所以推进一次、事后回退，而不是「按需推进 m 次」。

    破了会怎样：graph 重放时指针走的步数和录制时不一致 → buffer 布局错位 → 同样是静默算错，而且只在开了 CUDA graph 时出现，关掉就好了 —— 极难定位。

    来源：SGLang RFC #28511 明确记录了这条约束。

  • flush 边界对齐 radix cache 的 snapshot 边界

    推理框架会把 prefix 的状态做快照复用（radix cache）。快照必须能完整描述「到某个 token 为止」的状态。而 ReplaySSM 的状态是 S₀ + buffer 两部分 —— 如果快照点落在 buffer 中间，你存下的 S₀ 并不代表那个 token 的状态。

    破了会怎样：另一条请求复用了这个快照，从一个错误的 S₀ 出发 → 静默算错，而且跨请求污染。三条里最难查的一条。

    这就是 RFC 要改 attention/mamba/mamba2_metadata.py 的原因。

注意三条的共同点：破了都是静默算错，没有一条会抛异常。这决定了开发方式 —— 不能靠「跑起来没崩」判断正确，必须拿 fp64 递推基线逐步对齐，容差压到 1e-13 而不是 1e-2。这条教训第 2 课那个漏掉 a 的 bug（31.8% 误差）已经预演过一次了。

回滚为什么是精确的

第 1 课说过「回滚只需退指针」。现在可以把它说得更强。我验证了「接受 m 个 draft 后退指针」与「一开始就只跑那 m 个」的差别：

偏差 = 0.00e+00   （m = 0, 1, 2, … 6 全部） 不是 1e-15，是精确的零。

为什么能精确到零？因为被拒的 draft 从未参与任何计算。它们的 u 被算出来了，写进了 buffer 的槽位，但 h 没有把它们计入 —— 于是重建状态时的求和根本不遍历它们。它们不是「被减掉了」，而是压根没被加进去。

对照：为什么快照方案做不到

既有做法（Snakes and Ladders）给每个 draft 存一份完整 d×n state，回滚 = 恢复快照。它也能得到正确结果，但代价是每个 draft 一份 4dn 的搬运与显存。

ReplaySSM 的回滚之所以免费，是因为它把「有损摘要」换成了「原始输入」。摘要一旦吸收就无法反悔，原始输入可以选择不读。这是第 1 课那句「存输入而不是存摘要」在簿记层的兑现。

L 被两侧夹住

第 1 课你用算盘摸到过一个临界点：窗口太长时，读 buffer 的字节会吃掉省下的写回。现在把它算完整 —— 加上 flush 的摊薄写回，L 的账有三项：

每步搬运 = 4dn  (读检查点)  +  4·h̄·(d+n)  (读 buffer)  +  4dn / 周期  (flush 摊薄) h̄ 是一个 flush 周期内 h 的平均值。L 变大 ⟹ 第二项涨、第三项跌。所以存在最优值。

令导数为零（对 h̄ ≈ L/2 的稳态）：

L* = √( 2dn / (d+n) )  ≈  11  （d = n = 128） 数值扫描给出 L = 12，与解析式吻合。极小很平坦 —— L 在 8–16 之间收益都是 1.70× 左右。

而下界完全来自投机窗口：L ≤ 2T 时 h 还是 0 就触发 flush，buffer 一次都用不上；要让 buffer 真正非空，需要 L ≥ 3T。两侧一撞：

投机窗口如何通过 L 吃掉带宽收益（d = n = 128）
TL 的下界（3T）取该 L 时的收益
1（不投机）31.71×（可取 L≈12）下界不起作用
4121.71×刚好撞上最优值
8241.65×下界已超过最优值
16481.45×明显让利

投机窗口不是免费的 —— 它两次收费。

第一次在第 3 课：`T²` 的额外内积，每 token 开销 `1 + T/(2h)`。第二次在这里：`T` 抬高 `L` 的下界，逼你离开带宽最优点。两笔账互相独立，都要算。

读检查点 64 KiB
读 buffer 5.0 KiB
flush 摊薄写回 5.8 KiB
每 decode step 的平均搬运（非投机稳态，fp32）
合计75 KiB
基线 summary route，8dn128 KiB

flush 周期长度11 步

搬运账按非投机稳态算（每 forward 一个 token），T 只驱动下界、不进搬运账。否则投机把一次 forward 摊给 T 个 token 的收益（那是第 3 课的事）会把 L 的取舍完全埋掉。把 T 拉到 8 以上，看下界怎么越过最优值。

与第 1 课的关系。第 1 课算的是瞬时 h 的临界点 dn/(d+n) = 64；这里算的是周期平均。因为 h 在 0 和峰值之间来回，h̄ ≈ L/2 —— 所以对应到 L 的归零处是 2dn/(d+n) = 128。把算盘的 L 拉到 128，收益正好显示 1.00×，与第 1 课把 h 拉到 64 时看到的临界点是同一件事。

一个附带好处（未实测）。flush 把衰减前缀和的跨度夹在 ≤ L 个 token 内。前缀和有 cancellation 与下溢风险，跨度越短越安全 —— 所以 flush 除了省显存，可能顺带改善数值稳定性。这是推理，不是实测，需要用 recurrent baseline 在长序列上验证，留给 kernel 分支。

2. write_pos 每 forward 只前进一次，是为了满足什么？
3. flush 边界为什么必须对齐 radix cache 的快照边界？

5. L 的取值被哪两件事夹住？

检索练习（合上讲义）

第一题 · 画状态机。在纸上重画一轮投机解码的完整簿记流程。必须出现：判据、flush 做的三件事、write_pos 在哪里推进、接受 m 个之后指针停在哪。

第二题 · 反推后果。对每条不变量，说出「破了会怎样」。哪一条最难定位？为什么？

第三题 · 定 L。d = n = 256、T = 8。求：(a) 带宽最优 L*；(b) 投机给出的下界；(c) 两者冲突吗？（先算，再用算盘核对。）

1. 稳态 → 判据 h + 2T > L？ → 是则 FLUSH（汇总进 S₀、写回 HBM、h=0 且 write_pos=0）→ APPEND T 个 draft（write_pos 在此推进，且只推进一次）→ VERIFY（三角求解出 u、masked GEMM 出 y）→ 接受 m 个，write_pos 退到 h + m，h ← h + m → 回到稳态。全程 S₀ 只读，唯一例外是 FLUSH。

2. ① 覆盖仍需的输入 → 静默算错；② CUDA graph 重放时指针步数错位 → 静默算错，且关掉 graph 就好了；③ 快照点落在 buffer 中间 → 静默算错且跨请求污染。

最难定位的是第三条：前两条至少在单条请求内可复现，第三条要同时满足「某请求恰好在错误边界做了快照」+「另一请求恰好复用了它」，是并发相关的、不确定复现的污染。第二条次难，因为它有个极具误导性的特征 —— 关掉 CUDA graph 症状就消失，很容易被误判成「graph 的 bug」。

3. (a) L* = √(2·256·256/512) = √256 = 16。(b) 下界 3T = 24（2T = 16 是完全不可用的硬底）。(c) 冲突：24 > 16，投机窗口把你推离带宽最优点。

注意 d = n = 256 时 L* 从 11 涨到 16 —— 状态越大，能负担的窗口越长（因为省下的那次写回 4dn 也更大）。所以 L 不是一个常数，必须跟着 d、n、T 一起调。这正是 SGLang 把它做成命令行参数 --gdn-replayssm-cache-len 而不是硬编码的原因。

本课全部断言的数值证据在 code/verify_replayssm_identities.py 第 5 节（4 条，含一条「必须失败」）。
